# Fleet alarms

`alarm` starts one Effect worker under a nonblocking `alarm.lock` in the private state directory. It uses `lockf` with launchd and `flock` with systemd. The lock belongs to that state directory, not to copies on other hosts. Stop the old supervisor before copying the journal and starting the new one.

`alarm-plist` prints the launchd plist. `alarm-unit` prints a systemd service for the configured unit filename. Both run the lock-owning launcher. Systemd defaults to the user manager. `alarm.systemd.scope: system` requires dedicated non-root `user` and `group` and selects `multi-user.target`; the desk's kit installs it in `/etc/systemd/system` and uses the system manager to reload and enable it. The renderer does not install, reload, or enable either kind. Set `alarm.enabled: true` to run. `alarm-check` reports sanitized source readings and service state without writing alarm state or sending notifications. The CLI `doctor` also checks the configured supervisor. For systemd, an enabled alarm must be active and persistently enabled, not just `enabled-runtime`. These service checks do not feed the worker's issuer alarms.

`ops-digest` is a read-only summary. It does not append to or use the regular digest's `health.jsonl`. `ops-health --name <name>` checks the exact mailbox identity. Its `status: ok` means the mailbox snapshot is complete and has a live lease; it does not mean the agent is taking turns. `ops-health --service mailbox` reports the mailbox service and storage instead, with fixed service states, PID presence (not the PID), restart counts and memory limits.

## Lifecycle and delivery

One XState machine per stable key holds `ok`, `firing` and `recovered`. SHA changes, different diagnostic text and repeated known failures do not create new keys. A key sends on entry, a severity increase or the reminder interval (default 120 minutes). Recovery sends once with incident duration. Unknown measurements retain the previous alarm instead of claiming recovery.

The private stage directory holds `alarms.jsonl` at mode 600. Each changed checkpoint is appended and fsynced before dispatch. It contains machine states, measurement trackers, page claims and a durable outbox. Malformed history or non-private files block reads; the loop never discards history to forget alarms. Preparation failures retain one queued notice per incident/kind. Once prepared, the signed plaintext envelope is persisted before submission. Retries replay that exact envelope, preserving the mailbox's sender-DID/TID idempotency identity. Accepted deliveries are checkpointed individually. An earlier failed delivery blocks later messages to the same recipient, so a late fire cannot follow its own all-clear.

Each worker cycle owns a fresh scoped HTTP dispatcher. The dispatcher closes at cycle completion, failure or timeout; no pooled connection survives into the next cycle. Mail preparation already reloads the identity lease and constructs a service-auth client for each delivery. A failed or uncertain send leaves the sealed envelope pending for the next cycle, without resealing it. After five consecutive failed cycles, including notification failures, the worker writes its heartbeat and fails. The launcher propagates the failure as a nonzero exit. The generated plist has unconditional `KeepAlive` and a 60-second restart throttle. A successful cycle resets the failure count; restarting alone does not erase the persisted count.

Phone paging is optional. When `alarm.page` is omitted, the alarm sends the same Rat King notices but does not attempt or record pages. `alarm-check` reports `"page":"not configured"`. When configured, pages go to Joel's phone and grokbot, so they carry real incidents only. Warn never pages. A critical pages only when all of these hold: it is firing now, outside any maintenance window (a covered reading is `maintenance`, never `firing`); it is confirmed by two consecutive samples or five minutes of firing; and its owner has not acked it within ten minutes of `since`. No alarm ack transport exists yet, so the ten-minute wait always runs out (TODO: an owner ack). Each incident's id is its `since` in epoch milliseconds, printed as `Incident <id>` in every fire text. One incident pages at most once, even when its severity rises. When a paged incident clears, one page says `cleared <key> <id> after <seconds> seconds`. `mail.stranded/<name>` is warn-only and never reaches the operator gateway, including clears for earlier critical incidents. Ordinary mail wait and owner opt-ins never page. A key cannot reserve another fire page for six hours; all keys share at most six fire pages in a rolling 24-hour window. Clear pages do not count against either budget. Page records for a still-firing incident outlive the 24-hour window, so a long incident never pages twice. The page slot is reserved before the gateway runs, and a failure or uncertainty consumes it rather than risk a duplicate. Pages are independent of Rat King delivery, so a broken issuer can still reach Joel. Successful page execution requires exit zero and JSON `ok: true`.

## Configuration

`stage.json` owns all identities, recipients, paths, commands and owner mappings. Add an optional `alarm` section with:

- `enabled`: explicit boolean, initially false.
- `broadcast`: destination agent name for operator alarms, excluding retired wake alarms and owner-only opt-ins.
- `musterDesk`: the configured Muster desk name, included for `readers.*`, `issuer.*` and `mail.stranded/*`. A firing `readers.stuck` also goes to each stuck reader's owner, named in its heartbeat (`MUSTER_OWNER_NAME`). The all-clear goes to the static recipients only.
- `owners`: key or dotted-prefix to owning desk. The longest matching prefix wins. Recipient fan-out is deduplicated.
- `renotifyMinutes`: optional positive integer, default 120.
- `notify`: operator identity secret, directory path and optional Pi config path. The sender is always `operator`; its identity must match the directory's operator DID.
- `page`: Node executable and the approved notification gateway script path.
- Set exactly one supervisor. `launchd` takes `label`, `node`, checkout `source`, `path` (PATH), `outputLog` and `errorLog`. `systemd` takes `unit` (the `.service` filename) instead of `label`, plus the same remaining fields. Systemd needs absolute executable, checkout and log paths. Its user manager must start at boot for the alarm to run before login.
- `readerHeartbeats`: one entry per host, with a display `host`, the Pi state's `readers` directory as `dir`, and an `ssh` destination for every host but the alarm's own. The worker reads each host's heartbeats with one bounded call per check (10 seconds, `BatchMode=yes`). Pid liveness is checked on that host. If the list is omitted, reader monitoring is unknown, not healthy. If a host's directory is missing, that host has no readers. The older `readers` list with `aliveCommand` is ignored. It is accepted only so existing configs keep loading, so delete it when you add `readerHeartbeats`.

Optional `alarm.wakeTargets: [{ name, owner, unackedMinutes?, page? }]` preserves explicit owner opt-ins. The threshold defaults to `alarm.wakeUnackedMinutes` (15 minutes when omitted). Each overdue target fires `mail.owner/<name>` to its owner only, never to broadcast, the desk or the operator gateway. The legacy `page` option still decodes but no longer grants operator paging authority. Owner notices and their recovery use the normal durable outbox.

The same opt-in enables `reader.absent/<name>` when the lease has been absent for the threshold and admitted mail has been undelivered for at least that long. It reports the lease age and undelivered count to the configured owner. A live lease or empty backlog keeps it quiet. Unlike `mail.owner/<name>`, this alarm needs no process heartbeat and can page through the normal gate when the target sets `page: true`.

Optional `alarm.push: { names, secret }` enables APNs for the listed names. Put the secret reference in private stage config. The referenced credential is JSON with `keyId`, `teamId`, `bundleId` and the `.p8` PEM contents in `privateKey`. The alarm worker leases it at startup. An absent or invalid credential emits `push.unconfigured` once and disables push until restart. The mailbox does not call Apple. It returns one pending notice to this operator client only when the DID has registered a device and has no live lease.

Push is best effort. It picks the newest eligible message, coalesces during the one-minute per-name budget, and records the attempt before sending. A failed attempt does not retry that message. The journal stores message IDs, admission positions and attempt times, never tokens or previews. `push.sent` means APNs accepted the request, not that the handset displayed it. No APNs credential is needed for mail admission or foreground catch-up.

Use a fresh copy of the live stage config. Do not promote an older proposal that loses approval fields or notification recipients.

## Sources

- `ship.failed`: latest failed receipt; public SHA and sanitized cause. Missing/unreadable receipt history is unknown, not recovery.
- `ship.churn`: warn when more than `ship.restart.churnLimit` (default 3) ship receipts report a celld restart within the last 24 hours. It never blocks a restart. Missing receipt history is unknown.
- `celld.down`: two failed health checks outside a fresh `restarting` marker's 180-second window. The marker is read on the configured live node, not from the alarm host's filesystem. Unknown marker readback cannot prove that a restart window has ended.
- `celld.restarted`: ActiveEnter moves after the initial baseline without a receipt that reports a real restart spanning that instant. It remains firing until an explaining receipt appears. Deploy-time observations wait for receipt/window resolution. A maintenance window run by `celld-window.sh` appends a window receipt (`kind: "window"`, epoch-second `start`/`end`, reason, approval, result, before/after celld PID and ActiveEnterTimestamp) to `window-receipts.jsonl` beside the deploy marker on the live node; the alarm reads it there like the marker, skipping malformed lines; a restart inside `[start, end]` is explained. Window receipts are separate from ship receipts, so the ship judge never reads them. A missing or unreadable window file explains nothing.
- `doctor.unavailable`: warn only after continuously unavailable configuration checks spanning at least 15 minutes (`DOCTOR_UNAVAILABLE_SPAN_MS` in `alarm-config.ts`). The headline is "Configuration doctor unavailable; identity not checked". The first completed check, whether ok or fail, clears it and resets its timer. Shorter spells never page, including probe timeouts; doctor availability does not feed the generic measurement-failure alarm. The health digest counts unavailable readings since the previous digest and includes the last reason only when the count is positive. The alarm journal retains a cumulative count and last reason across recovery; each digest stores its count cursor. Old journals and digests start at zero. A reset counter contributes its new value rather than a negative delta. Digest reads use the bounded alarm-journal reader.
- `issuer.broken`: critical only after at least three consecutive failed configuration checks spanning more than two minutes. Both gates must pass (`ISSUER_FAILURE_CHECKS`, `ISSUER_FAILURE_SPAN_MS` in `alarm-config.ts`). A decoded doctor failure or nonzero node exit counts as a failure. SSH exit 255, timeouts, process startup errors and undecodable results are unavailable readings, not configuration failures; they reset the failure streak and clear `issuer.broken`. A healthy result clears it. Diagnostics distinguish SSH transport, node exit, timeout and decode steps. Nonzero exits include a redacted stderr tail of at most 300 UTF-8 bytes, never configuration contents. Only pre-session mux errors with empty stdout retry once with `ControlPath=none`; master read failures never retry.
- `instance.down`: requires two consecutive misses per instance (`INSTANCE_DOWN_CHECKS`). The first miss is unknown, not a fire or recovery. Confirmed misses warn unless that instance opts into critical paging. A healthy sample resets its count. Existing maintenance and operator paging gates still apply.
- `readers.stuck`: warn when a heartbeat's pid is alive and its reader has made no lease or consume progress for over 5 minutes. Progress is `lastConsumeOk`, or `startedAt` before the first lease. Evidence names each reader, its host, state, last error tag and idle minutes. A heartbeat whose pid is dead is stale and ignored. A SendOnly heartbeat is also ignored when that name's operator nameHealth snapshot positively shows an unexpired lease held by a different session. Missing session or lease evidence, expired leases, same-session holders and non-SendOnly states remain eligible for the warning. The collector reuses its existing per-name health reads. An unreadable host makes the reading unknown, unless another host already shows a stuck reader.
- `wake.unacked`: retired. Existing journal states still decode. The first cycle drops the old state, queued notices, pending deliveries and page records without sending a fire or clear.
- `mail.stranded/<name>`: warn only when wake mail is older than four hours and a current matching heartbeat proves a real reader. A live pid warns only when its current holder has an observed turn start older than four hours. A dead pid warns only when its heartbeat records a lease or consume within the last 24 hours; exactly 24 hours is stale. Closing a row removes its heartbeat, so a lease alone cannot authorize a wake. Missing turn evidence does not prove inactivity. Retired names are silent. The collector reads the optional `retired` flag in each target's operator `mailbox.nameHealth` response, alongside its existing mailbox snapshot. It never scans the fleet's retirement list during an alarm poll. Older mailboxes omit the flag; that remains unknown and cannot dispatch a mail warning. Missing reader-existence evidence retires a stale incident even when retirement metadata is unknown. If the entire wake-health source is unavailable, an existing warning and its outbox expire silently 24 hours after the last recorded warning. The digest alone may make one full retirement scan per run, and only when observed mailboxes lack the new flag. That scan has the normal 90-second operation budget; individual HTTP requests retain their ten-second budget. `identity.listRetired` validates at most eight mailbox records concurrently and preserves cursor order and stale-projection pruning. Its existing name-primary-key cursor needs no schema migration. Deploy the additive mailbox projection before the alarm client to restore warnings for current readers; mixed versions stay silent rather than guessing. Stale dead heartbeats, lease-only names and other abandoned mailboxes contribute one `abandoned mailboxes: N (oldest …)` digest line without changing digest status. Retired names are excluded from that count. Digest collection includes remembered journal targets after their heartbeat disappears. Each real reader still has its own warning and recovery lifecycle. Existing critical states, notices, deliveries and page claims for stranded mail are removed silently before reclassification, so this change cannot send a phone fire or clear.
- Cross-restart re-delivery is not inferred from a lease generation change. The current health projection exposes message IDs and lease generations, not consume-attempt history. Follow-up: record consume-attempt receipts with message ID, recipient name, a reader-instance ID minted on reader startup, lease generation, attempt time and ack time. Expose only this metadata through an operator read endpoint. Retain receipts while the message is unacked. Page only when the same unacked ID has confirmed attempts from two distinct reader instances, not merely two lease generations; ack or drain clears that reader’s incident. This requires mailbox-owned data, not journal guesses.
- `filer.slots`: free/max below 10 percent, critical below 5 percent. Missing values or zero capacity are unknown.
- `quarantine.growth`: more than twenty files with fresh modification times in the preceding hour, summed across both configured quarantine roots. The quarantine-only collector does not read sessions or route receipts.
- `digest.fail`: latest digest is fail, or a source measurement was unavailable. Missing history is unknown. Inside an active backup cover, unavailable measurements read as maintenance rather than firing. The next digest includes that maintenance evidence while the cover is still active. A failed digest or an independent stop-memory failure still warns inside the cover. Outside the cover, unavailable measurements warn after two misses. Inside a mailbox maintenance window, missing stop-memory accounting is planned (celld is stopped), so it does not warn.

## Maintenance windows

Anyone restarting a Rat King instance declares the window first, on the alarm host:

```
nest maintenance start --instance mischief --until 16:40Z --owner pi-durable/desk --reason "Jev key deploy" [--grace-minutes 5]
nest maintenance end --instance mischief
nest maintenance list
```

`--instance` is a configured `alarm.instances` name or `mailbox`, the stage's own celld. `--until` takes `HH:MMZ` (the next time the UTC clock shows it), `+30m`/`+2h`, or an ISO time with a zone. It must lie in the future and at most 12 hours out, so a typo cannot hide an outage. Grace defaults to 5 minutes. A new window for an instance closes its open one; `end` closes it now, and grace still runs from then. The file is `maintenance.json` in the stage state directory, mode 600, replaced atomically. The alarm reads it on every tick, so a declaration takes effect without restarting the daemon. A missing file declares nothing. An unreadable file declares nothing, and the alarm names `maintenance` among its unavailable measurements.

For a separate alarm service account, set `alarm.maintenanceInbox` to `{ "path": "<absolute read-only request directory>", "operatorUid": <numeric local operator uid> }`. The alarm refuses a symlink, a different directory owner, or a directory writable by group or others. Give its group read/traverse access. Publish a regular operator-owned file atomically in exact mode `0640` as `<id>.json`, no more than 4096 bytes, with exactly `id`, `action`, `instance`, `until`, `owner`, and `reason`. Match the ID to the filename: 20 decimal digits of Unix nanoseconds, a hyphen, and 32 lowercase hexadecimal digits. `owner` is attribution asserted by the trusted operator, not a second authenticated identity. The drop's group must match the alarm group on the inbox directory. I/O, UID, GID and mode faults defer for ten minutes from the ID timestamp, then produce one refusal. A future timestamp defers on first sight; a later tick refuses it if it is still more than five minutes ahead.

A `start` needs a UTC ISO `until` in the next four hours. An `end` uses `until` only as the request's expiration; the window ends when applied. Both reject IDs more than four hours old, even without the journal. While the files remain, a later trusted end from the owner or desk blocks replay of an earlier start for that instance, even after the end request expires. Only the current window owner or configured `musterDesk` can replace or end an open window. The inbox uses five minutes of grace. Inbox mode refuses direct `nest maintenance start` and `nest maintenance end`; `nest maintenance list` remains available.

The alarm commits each decision with its window update in private `maintenance.json`. It queues an accepted/refused notice to `musterDesk` and retries the same stored envelope on uncertainty. Mailbox admission deduplicates exact envelopes by recipient mailbox, sender DID and message ID (`apps/mailbox/src/mailbox.ts`, send transaction). A permanent preparation failure replaces the original notice with a generic refusal; if that also cannot be prepared, the alarm records the terminal decision and logs only a sanitized failure. A recorded name never reapplies while it remains in the inbox. The alarm does not remove or acknowledge inbox files; cleanup belongs to the kit. Only sent or dropped decisions older than 24 hours are pruned after their files disappear. Pending notices survive cleanup. Request contents and paths are not logged. Preserve `maintenance.json` with its request journal when migrating or rolling back. Run only one writer at a time.

Set `alarm.maintenanceLookup: true` to resolve an exact configured `musterDesk` missing from the local snapshot. It uses the existing, pinned alarm signer to call authenticated `identity.listNames`. The signer and any pinned name or alias stay local. The lookup accepts only an exact non-retired row whose DID matches its validated document. It reads up to four pages of twenty rows, with a four-second total deadline and a 256 KiB response cap per page. An exhausted search or an exact retired row is a refusal. An auth or transport error, invalid response, or incomplete search defers the notice. A prepared notice is never resealed to a different recipient. This does not refresh the directory or change ship, wake, or any other alarm target.

Set `alarm.maintenanceStatusPath` to a normalized absolute filename for a redacted JSON snapshot. The kit pre-creates its dedicated parent under trusted ancestors, owned by the alarm writer and operator read group, mode `2750`. The writer atomically publishes group-readable `0640` snapshots. There is no directory creation, path export, or change to the private journal's mode. The snapshot has `version: 1`, generation and heartbeat times in Unix milliseconds, the heartbeat outcome and age at generation, disabled `alarmSources`, windows still in effect (including grace), and recent decisions and notice delivery states keyed by request ID. Compute present heartbeat age from `heartbeat.at` and check `generatedAt` for stale exports. Legacy decisions without recorded outcomes are `unknown`, even if the notice was sent or dropped. Up to 64 windows and 128 requests fit, with a 64 KiB total byte cap and `truncated` marker. Status export failure leaves the last good file in place and logs no inputs. Both options are off when omitted.

Set `comms.remote` or `doctor.secondary` only when that source is reachable from the alarm host. An omitted source isn't probed and adds no finding. `alarm-check` labels the omitted source `not configured`; if the entire doctor block is absent it reports `doctor.primary` as `missing` instead. `nest done-bar` checks only the configured comms sources.

Use `alarm.sources` to turn off a measurement the alarm host cannot make. Each key defaults to `true`: `doctor` controls `issuer.broken` and `doctor.unavailable`, `quarantine` controls `quarantine.growth`, and `receipts` controls `ship.failed` and `ship.churn`. For a host without those inputs:

```json
{ "sources": { "doctor": false, "quarantine": false, "receipts": false } }
```

`alarm-check` reports affected readings as `off`, not healthy or unavailable. Off readings do not clear existing incidents. Digest and health JSON report disabled sources in `alarmSources`. `digest` skips the doctor when it is off. Both digests use `quarantined_24h: null` when quarantine is off, but still read comms delivery receipts. The `receipts` switch only disables ship receipt history, not the deploy marker or maintenance window receipts. An enabled but missing input still fails its check. Explicit `nest doctor` and `nest done-bar` keep their existing checks.

Inside a window (from start to end plus grace), `instance.down` for that instance, and `celld.down` for `mailbox`, read `maintenance by <owner>, ends HH:MMZ`. That goes once per window, quietly, to the owner only: no broadcast, no Muster desk, no page. A mailbox restart inside the window explains `celld.restarted`. The alarm machine holds its state through a maintenance reading, as it does through an unknown one. A window covers only its named instance and only until its end plus grace. After that the alarm runs as usual, and if the instance has not been seen up since the window ended, the evidence adds `overran maintenance by <owner> (<reason>) that ended HH:MMZ plus N min grace`. Overruns page through the normal gate.

The backup is an implicit `mailbox` window owned by `backup`, including manual runs. It starts at the validated backup unit's `ExecMainStartTimestamp` and ends at the earlier of unit exit or `backupStopBudgetMs` from [`backup-limits.ts`](backup-limits.ts). That shared bound adds the maximum precopy budget, the arm slack and the stop/restart allowance. The arm guard uses the same bound and refuses a stop without enough remaining cover for stop and restart. It also refuses a missing, future, pre-unit or twenty-minute-old precopy completion and rechecks both deadlines after restart-marker fsync. A backup still running past that budget alarms as an overrun. Backup windows have no owner to notify, so they send nothing; `alarm-check` shows them as `maintenance`. Health digests taken inside the backup's stop budget list stopped celld or SeaweedFS, mailbox health and missing memory accounting as `maintenance by backup: …` reasons that do not change the digest status.

Precopy uses preflight bytes: 25 minutes plus one minute per started GiB over 100 GiB, capped at 90 minutes. Its script alarm expires ten seconds before the outer Effect timeout. A computed budget above the cap emits `BACKUP_PRECOPY_CAPACITY`; the health digest carries a capacity warning for that invocation even if the backup succeeds. Expiry fails before arming or stopping mail. The unit's ten-hour timeout is the explicit global cap, not a promise that every byte-scaled pack and transfer timeout fits cumulatively. Pack and transfer run after mail has restarted.

Source probes have bounded deadlines. The worker targets a 60-second cadence and bounds each cycle at 55 seconds. There are no service-control actions, listener processes or recovery automation in this loop.

## Qualification

Run property/model tests, then `alarm-check` and `doctor` with approved private selectors. Confirm the expected supervisor is active, systemd is persistently enabled if selected, and each configured host's heartbeats are read. After cutover, prove one synthetic alarm and one wake under live-message approval. Roll back by stopping and disabling the new job, transferring the current journal back and restoring the previous job. Never leave both jobs active.

Untested by this lane: live fan-out, a real Joel page, launchd restart supervision and the ssh path to a remote heartbeat host. The property suite covers lifecycle/restart replay, stable-key dedupe, page budgets, source thresholds, deploy grace and encoded envelope replay. Filesystem quarantine freshness uses modification time, not a claim about file birth time.

## Crash notices: retries, refusals and logs

- A crash notice whose recipient the mailbox refuses as `Retired` or `UnknownName` is terminal. With a successor named in the refusal, the notice is re-sealed to the successor once. Otherwise, or if the successor refuses too, the key moves to `sent` and is recorded under `dropped` with the reason.
- Other send failures back off per entry: 2 s doubling, jittered down by up to half, capped at 10 minutes. The journal's `attempts` and `nextAt` are optional, so older journals read as due now. Only the first failure and the recovery are logged.
- The alarm and ship runners exit for a supervisor restart when the ship checkpoint's `successful` sha changes, meaning a commit from `origin/main` was deployed. Commits made in the local checkout do not restart them.
- Once per cycle the worker checks `alarm.out.log` and `alarm.err.log`. Past 16 MiB it gzips the file's current bytes to `<name>.<utc>.log.gz` beside it, fsyncs the archive, and truncates the live file. The supervisor keeps appending through its open descriptors, so renaming would send new output into the archive. Copy then truncate keeps those descriptors valid. Archives older than 30 days are removed. The first rotation after deploy archives the existing large log.
